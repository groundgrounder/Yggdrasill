# 路由

路由是内核中每轮只读的计算，为叙事模型组装上下文。第四章说明了路由所依据的读取：它经协议读取有效本局，每轮只求解一次。本章说明上下文由哪些部分组成，在场者、被提及的角色、条目、经历与候选，各自怎样选入、怎样排序，预算怎样限制选入，上下文怎样写成文本，审计记下什么，最后以示例“雾港”的一轮上下文串联上述内容。上下文各部分的输出字段、审计与运行参数的逐项清单，见参考“路由”。路由只读，不写任何变量。世界书、本局、消息与运行参数相同时，得到的上下文也相同。

## 上下文

路由的输入有三项：本局变量；最近的消息，即从旧到新排列的一组文本；运行参数。输出有两项：上下文，以及只给作者看的审计。读取都经协议，在有效本局上进行，待登记事件视为已经发生，它写入的状态都看得到。上下文先组装为结构化的数据，再由渲染写成文本。

上下文依次由七个部分组成：

| 序 | 部分 | 预算 |
|---|---|---|
| 1 | 协议文本 | 不限 |
| 2 | 世界概况 | 不限 |
| 3 | 世界当前状态 | 不限 |
| 4 | 在场角色 | 不限 |
| 5 | 被提及角色 | 不限 |
| 6 | 条目 | 每个条目库各有字符预算 |
| 7 | 事件：已确认经历、待登记、候选、待初始化 | 经历与候选各有条数与字符预算，待登记与待初始化不限 |

没有内容的部分省略。协议文本在打包时由模板生成，每轮原样输出，依次是变量更新规则、角色通用约束与扮演准则，以空行分隔（见第一章“生成”）。世界概况是 `世界概况/` 下各文件的原文，按文件名的码点顺序。世界当前状态有当前时间、当前地点、剧情标记与有值的二层世界字段。进行中的事件串，按事件串ID的码点顺序，各附概述，以及本串状态为 1 的事件，每项写作“事件标题：分支结果”，按实际时间先后。还有待定项，原样输出。进行中的事件串因此不经经历的选入，也不受经历预算的限制。

运行参数控制上下文的规模，不属于任何一层，写在项目根的 `yggdrasill.yaml` 中，文件中只有“运行参数”一个映射，不写时取默认值：经历的条数与字符，默认 6 条、3000 字符；候选的条数与字符，默认 4 条、4000 字符；条目的字符，默认每库 1500，可以按库名单独设置，库名须是已声明的条目库；提及窗口，默认 2 条消息。未知的键，或取值不是非负整数时，报错。

预算是对上下文中某一部分的限制，不是整个提示词的上限。每项的字符数，是该项序列化为 JSON 之后的 Unicode 码点数。一部分的用量，是入选各项之和。字符数不是 token 数。只有经历、候选与条目受预算约束。

## 在场者

七个部分中，在场角色以后各部分的内容都由路由逐项选出。在场角色一部分列出在场者，即视为在场的已启用角色组，按角色组ID的码点顺序排列，自建的玩家排在最后。每个在场者输出：角色组ID与显示名；年龄，即当前时间的年份减去出生年，没有出生年或当前时间时省略；当前档案的基本信息与角色印象，剥离机器字段，技能补充只留可用技能的项；当前能力与可用技能；本局状态，即角色变量中的二层字段与装备，不含在场、所在、能力维度、能力移除记录与已初始化。扮演角色组另标为玩家扮演，叙事模型不替它决定言行。

档案冲突或解析异常的角色组，只输出角色组ID与显示名，原因记入审计。自建的玩家输出角色组ID“玩家”、显示名、年龄、开局设定中的玩家档案、当前能力、可用技能与本局状态。显示名取档案的姓名，没有时为“玩家”。

在场者中，初始化方式为显式确认、有待初始化预览的角色组，另在事件一部分的“待初始化”中输出角色组ID、档案ID与预览，空起点也列出，等叙事模型以命令确认。出场自动的不列，它们在写入时自动初始化。

## 提及

不在场的角色组、条目与事件，是否进入上下文，取决于最近的消息是否提到它们。路由在最近的消息中，只看最后若干条，条数由运行参数“提及窗口”规定。窗口之内，路由查找哪些角色组、条目与事件被提到：角色组按显示名与别名，包括所选版本的显示名与别名；条目按 ID 与名称；事件按事件ID与事件标题。查找是在文本中逐字匹配，不分词，称呼出现在更长的词中也算提及。每项记下首次出现的位置，即第几条消息、第几个字符。

已启用而不在场的角色组被提及时，列入被提及角色，只给角色组ID、显示名与别名，不给档案，按首次出现的位置排序。被提及而未启用的角色组不进入上下文，记入审计。被提及的条目是条目的一种来源，被提及的事件是经历的第一种入选理由，见后文。

## 条目

在场者、地点链与提及，共同决定条目一部分选入哪些条目，输出它们的条目正文。条目按三种来源依次选入，同一条目只选一次，以先选入的来源为准：

1. 本局状态引用：在场者的本局状态与集合维度中，按声明引用了条目库的值与映射键，例如持有的装备、职位所属的势力、天赋中的技能。按在场者的顺序、字段声明的顺序与值的顺序。
2. 地点链：当前地点的地标及其各级上级，从地标往上（见第一章“条目库”）。
3. 提及：提及窗口内出现条目ID或名称的条目，按首次出现的位置。

技能另须是某个在场者的可用技能，不可用的技能不展开，记入审计。按种类分的库，条目前面附上它所在各级目录的说明文件，库的根说明在前，每份说明只输出一次。按上下级分的库，只附根说明。说明与条目一起计入预算。

每个条目库有自己的字符预算。条目按选入的顺序放入，放不下的整条略过，接着试下一条，不截断。输出按条目库声明的顺序分组，组内按选入的顺序。

## 经历

事件一部分有四项：已确认经历、待登记、候选与待初始化。已确认经历，即经历，从有效本局中状态为 1 的预设事件与动态事件中选入，不含首次登场初始化的记录，也不含待登记事件。事件须有下列理由之一才入选，按所具有的最高理由定优先级：

| 优先 | 理由 | 条件 |
|---|---|---|
| 1 | 点名 | 提及窗口内出现事件ID或事件标题 |
| 2 | 候选前置 | 某个已选入的候选，其门槛以正向引用依赖它，见下文 |
| 3 | 当前地点 | 事件的地点与地点链有交集 |
| 4 | 共同经历 | 实际参与者中至少两个是在场者 |
| 5 | 在场者经历 | 实际参与者中至少一个是在场者 |

候选前置只认成立的路径上的引用。成立的路径，指从门槛的根向下，只进入求值为成立的节点。路径上只认正向引用，处于否定之下的引用不算。候选所附分支的门槛同样计入，只看门槛成立的分支。候选前置因此是候选得以成立所依据的已确认事件，候选的选入见下一节。

同一理由之内，点名按首次出现的位置排列。其余依次按在场的实际参与者人数从多到少、实际时间从近到远、事件ID的码点顺序排列。经历按此顺序放入：超出条数上限的略过。超出字符预算时，先去掉角色位置，仍放不下就整条略过，接着试下一条。入选的经历按实际时间先后输出，同时刻按事件ID的码点顺序。

每项经历输出事件ID、事件标题、事件概要、影响范围、实际时间、所走分支的分支结果、公开信息、隐秘信息，以及在场者的角色位置，角色位置的取法见第三章“角色位置”。隐秘信息属实，但只有知情者知道，这一含义由角色通用约束向叙事模型说明。动态事件只输出事件ID、摘要与实际时间。

待登记事件全部输出在“待登记”中，按求解的顺序，每项与经历的完整形式相同，另标为已经发生，不受预算限制。

## 候选

经历的候选前置所依据的候选，按以下规则选入，路由先选定候选，再选入经历。候选从有效状态为候选的预设事件中选入。满足下列之一即入选：有核心参与者在场，事件的地点与地点链有交集，事件没有核心参与者。三者都不满足的，记入审计，不进入上下文。

候选依次按以下各项排序：属于进行中事件串的在前，地点与地点链有交集的在前，在场的核心参与者人数从多到少，触发时间最晚从早到晚，事件ID的码点顺序。按此顺序放入，超出条数上限或字符预算的整条略过，不去掉角色位置。

每项候选输出事件ID、事件标题、事件概要、影响范围、叙事条件、公开信息、触发时间最晚，门槛成立的各分支，每个分支写分支ID、分支条件与分支结果，以及在场者的角色位置，只留角色定位、介入条件与事件触发语料，适用分支须与这些分支有交集。隐秘信息、角色知情与主观记忆不输出。

## 渲染

组装好的上下文由渲染写成文本。默认的渲染以每一部分的名称作包裹标签，例如 `<协议>`、`<世界状态>`、`<在场角色>`、`<条目>`、`<事件>`。协议文本与世界概况原样放入，其余部分以 YAML 写出，每一项写出自己的名称或 ID。标签名集中在一张表中，适配层可以替换。机器字段在组装时已经剥离。源文件中单独成行的包裹标签由检查器报错，以免与渲染的边界混淆，见第一章“文件”。

## 审计

上述各部分的选入与略过，都记在审计中。审计是路由每轮留给作者的记录，不进入上下文。审计逐部分记下：选入的项与理由，经历与候选另记形式，即完整还是去掉了角色位置；略过的项与原因，例如无关联、超出条数、超出字符、技能不可用、条目不存在；受预算约束的经历、候选与各条目库，另记字符用量与预算。审计另记提及的结果，包括被提及而未启用的角色组，以及异常，例如档案冲突、解析异常、当前地点不在地点库中。作者据审计查明某项为何进入或没有进入上下文。

## 实例

下面以示例“雾港”的一轮上下文说明上述规定。

### 输入

以潮历072年开局，叙事模型以写场景把当前地点写为灯塔的值守室，学徒与秦守在场，此时秦守出场自动初始化。最近的两条消息是：

```
棠小姐托人来问，雾季的灯号会不会改。
秦守在值守室里讲起灯语·长夜信号的手法，又提到航海·夜航的规矩，说周书记过几天要上来看灯。
```

运行参数取默认值。这一轮的上下文七个部分俱全，渲染之后的文本共 8607 字符，含包裹标签与 YAML 的换行。以下各部分的数字按各自的算法计，不能直接相加。协议文本 2737 字符，世界概况两份文件 174 字符。其余五个部分的 JSON 码点数，世界当前状态 191，在场角色 1791，被提及角色 40，条目 769，事件 1737。受预算约束的部分中，经历用去 3000 中的 1020，候选用去 4000 中的 635，技能、装备与地点三库各用去 1500 中的 374、142 与 221。

### 状态

世界当前状态写当前时间潮历072年、当前地点灯塔的值守室、剧情标记灯塔状态重燃与雾季已至，以及天气为雾。进行中的事件串只有学徒修习，附概述与本串已确认的两个事件，写作“灯塔收徒：学徒搬到灯塔，成为秦守的徒弟。”与“夜间值守：学徒熟悉了夜间灯号和交班节奏。”，前者是拜师的事件标题。本局没有待定项。

### 人物

在场角色依次为灯塔学徒、秦守与玩家。灯塔学徒的显示名取所选版本的显示名林澜，出生年为潮历058年，年龄 14。当前能力为灯语熟手、天赋雾中视·辨影与习惯“每刻钟查一次灯芯”，可用技能为灯语·短讯与雾中视·辨影。本局状态有关系、好感度、身份与知识。秦守年龄 63，刚完成初始化，当前能力为灯语名匠、修船匠人与名望匠人，可用技能为修船·补帆、灯语·短讯与灯语·长夜信号，本局状态有关系、好感度与装备工具·铜扳手。玩家是自建的空档案，显示名为“玩家”，没有年龄。当前能力只有空的天赋与习惯两个集合维度，可用技能为空，没有本局状态。灯塔学徒是显式确认，当前档案学徒期的预览为空起点，列在待初始化中。

提及窗口包含这两条消息。第一条中的“棠小姐”是白棠的别名，白棠已启用而不在场，列为被提及角色，只给角色组ID、显示名与别名。第二条中的“秦守”指在场者，不另列。“周书记”是周岚的别名，周岚未启用，不进入上下文，记入审计的未启用一项。

### 条目

技能库选入两个条目：雾中视·辨影，来自学徒天赋这一集合维度的本局状态引用；灯语·长夜信号，来自第二条消息的提及，它是秦守的可用技能。同在第二条消息中的航海·夜航，在场者都不能用，记为不可用而略过。技能库按门类分，两个条目前面附上库的根说明，灯语·长夜信号另附“灯语”一类的说明。连同说明，雾中视·辨影 184 字符，灯语·长夜信号 190 字符，共 374 字符。装备库选入秦守持有的工具·铜扳手，附根说明，共 142 字符。地点库选入地点链灯塔、雾港与北湾，附根说明，共 221 字符。白棠的职位引用势力库中的白帆商会，但白棠不在场，势力库没有条目选入。

### 事件

候选有两个，都因核心参与者在场而入选。出师考核属于进行中的学徒修习，排在前面，附上门槛成立的两个分支，以及两人的角色位置：学徒只有角色定位，秦守另有事件触发语料“灯号错一次，船就少一条。”，角色知情与主观记忆没有输出。秦守讲旧事不属于进行中的事件串，排在其后。它没有角色位置的文件，不附角色位置。秦守在场，名望为匠人，分支“讲述并示范”的门槛“在场实力人数”成立，两个分支一并附上。

经历的候选池有六个事件。夜间值守的理由是候选前置：出师考核的门槛正向引用它，且在成立的路径上。拜师、学徒守灯与大雾之夜的理由都是当前地点，三者的地点灯塔或北湾在地点链上。同一理由之内，拜师在场的实际参与者有两人，学徒守灯一人，大雾之夜没有，依次排列。拜师本可算作共同经历，按最高的理由定为当前地点。接手商会账目与白棠在码头没有任何理由，记为无关联而略过。四项按实际时间先后输出：拜师、夜间值守、大雾之夜、学徒守灯，大雾之夜与学徒守灯同在071年04月20日，按码点顺序排列。拜师与学徒守灯带有在场者的角色位置，拜师中学徒的角色位置有角色知情，秦守的没有。

### 预算

同一轮把经历的字符预算改为 220：夜间值守 110 字符先入选；拜师完整时 372 字符，去掉角色位置后 136 字符，仍放不下，整条略过；学徒守灯与大雾之夜同样超出字符而略过，用量 110。改为 246 时，拜师去掉角色位置后正好放下，用量 246。把经历的条数改为 2，夜间值守与拜师完整入选，学徒守灯与大雾之夜超出条数。把候选的条数改为 1，只选入出师考核，秦守讲旧事超出条数。把技能库的字符预算改为 184，雾中视·辨影连同根说明 184 字符，恰好放下，灯语·长夜信号超出字符而略过。这些略过都记在审计中，并写明原因。
