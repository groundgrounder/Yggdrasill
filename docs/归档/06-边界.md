# 边界

前五章说明了世界树的机制。每一项机制都有它适用的范围，范围之外的事，或者由别的部分承担，或者留给作者判断。本章依次说明这些范围：世界书能表达什么；检查器能保证什么；哪些部分依赖叙事模型；上下文的规模由什么决定；哪些部分留给适配层；最后以示例“雾港”中的几次实测串联上述内容。每一项先写现有的做法，再写它所覆盖的范围。

## 表达

世界书以固定的形状表达规则。条件类型属于第一层，共十一种，卡不能另增；技能是否可用，只有等级门槛与集合持有两种规则形状，第二层只填参数。程序因此不解释作者写下的公式或脚本，同一套内核能检查、运行所有的卡。两种形状之外的判断，例如同时看两个能力维度，不由程序计算，只能写进技能的文本，由叙事模型把握（spec/03、06）。

能力维度有等级映射、单值等级与集合三种类型，没有数值型的维度。数值只作为本局变量的数值字段，例如好感度，以增加与减少写入，结果截断在值域之内；门槛中的条件“角色状态”只读有取值表的本局字段值，例如关系阶段，不读数值，按数值的高低设门槛不在表达的范围之内。维度之间相互独立，不由一个维度的值推出另一个（spec/03、06、09）。

事件没有持续时间：每个事件只有一个实际时间，持续的过程由事件串表达。条件“当前时间”只能比较小于或大于等于，剧情标记只能比较等于或不等于（spec/06、07）。

档案只记稳定的设定，状态记在本局。档案的切换依据档案的生效条件，生效条件中的事件确认引用的是预设事件；动态事件写入的身份、关系与能力，进入本局状态，却不使当前档案改变（spec/04、05）。

协议中没有随机。封卷按默认分支与书写顺序决出开局之前的历史，同样的开局选择总是得到同样的本局；本局之间的差别，来自开局的选择与叙事模型在游玩中的确认。版本与启用在封卷时写入开局设定，此后只读，游玩中不能更换版本，未启用的角色组也不能在游玩中加入（spec/12、15）。

## 检查

世界书写成之后，由检查器检查。检查器先做静态检查，再以协议抽样，结果分错误与提示两级，提示由作者判断（spec/13、15）。

静态检查核对结构与引用，不核对含义。取得身份的档案是否引用了实际达成结果的分支，条件文本的适用范围是否因改写而变化，角色知情与主观记忆是否与所适用的分支一致，文本是否替事件断言了本局的状态，都由作者核对。文本字段的检查限于禁用词、系统视角的措辞、破折号、陈旧的写法、规定的形式与长度（spec/04、06、10、13）。

事件与分支是否可达，按乐观假设判断：除事件确认与事件串状态之外的条件都视为可能成立。乐观假设下仍不可能成立的，检查器提示；判为可达的，只是不被排除，不保证在某一局中会发生（spec/07）。

抽样以有限的开局试验世界书。抽样年份取各事件触发时间最早与最晚所在的年份，各取该年与下一年，另加其中最早年份的前一年，开局时间写到年；运行抽样只试默认开局，以及全部角色组启用、各取第 i 个版本的组合；开局方案各封卷一次；开局选项每次只试一项，不试几项的组合。其它开局时间与配置下的封卷，抽样不覆盖（spec/15）。

档案互斥的抽样不看事件的门槛，在所枚举的全部状态组合上解析档案，其中包括实际不可能出现的组合；在这些组合中出现的冲突同样报错。组合超过 4096 种时，检查器提示并跳过该版本，这个版本的档案互斥不再核对（spec/15）。

影响面只沿事件门槛中的事件确认推算，经由剧情标记、事件串状态或角色状态的间接影响不计入（spec/12）。

## 模型

检查器检查的是世界书，游玩中的写入由叙事模型提出。叙事模型以命令写入本局，协议校验命令是否合法：路径、操作与取值是否符合声明，角色组是否已启用，事件是否为候选，所选分支的门槛是否成立。命令所写的内容是否与叙述一致，协议不判断。动态事件可以写入任何可写的字段，只受取值范围与单次增减上限的约束（spec/15）。

条件文本，即叙事条件、分支条件、介入条件、触发情境与触发限制，由叙事模型判断是否成立。隐秘信息属实而只有知情者知道，这一分寸由角色通用约束说明，由叙事模型把握。当前时间何时推进、事件何时确认、待初始化何时确认，都由叙事模型决定；条件确认与仅作候选的事件，窗口结束时没有确认即排除，不再出现（spec/06、10、15）。

## 上下文

叙事模型每轮读到的是路由组装的上下文，上下文的规模由预算与世界书共同决定。预算按 JSON 的 Unicode 码点数计，不按 token 计；它限制的是经历、候选与各条目库，不是整个提示词。协议文本、世界概况、世界当前状态、在场角色、被提及角色、待登记与待初始化不受预算约束，在场者越多、档案越长、世界概况的文件越多，上下文越长（spec/14）。

提及在最近的若干条消息中逐字匹配，不分词。别名越短，越容易出现在别的词中，被误认为提及；提及窗口之外的消息不再参与匹配。被提及的角色组只给角色组ID、显示名与别名；它的经历，只有在满足点名、候选前置、当前地点或在场者参与等理由时才进入上下文（spec/14）。

## 适配

上下文与命令在具体运行环境中的形态，由适配层决定。内核规定上下文的组成与命令的语义，不规定它们在某个运行环境中的形态。打包时合成角色卡与卡面内容，开局前端呈现开局选项并以协议预演封卷，存档与回档保存本局，从回复中解析命令并决定执行的时机与失败的反馈，以及替换渲染的包裹标签，这些都由适配层完成，另有设计文档（spec/11、14、15）。

本局只有经过协议写入，才执行校验、待登记的登记、初始化与排斥检查。适配层若绕过协议直接改动本局变量，例如直接改写当前时间或所在，读取时待登记事件的分支会按改动之后的状态选出，可能与窗口结束时的状态不一致（spec/15）。

## 实例

下面以示例“雾港”中的几次实测说明上述范围。实测都在示例的副本上进行，或只读取示例。

### 检查

把林澜·守塔期的生效条件改为“拜师以‘未拜师’确认”。这份档案写的是守塔的身份，所引的分支却是没有拜师、留在码头，含义不符；检查器的结果仍是 0 错误、0 提示，因为条件的结构、引用与正向的事件确认都合法。

为林澜另加一份档案“码头期”，以少年期为前置，生效条件为“拜师以‘未拜师’确认”。正式守灯的门槛要求出师考核或补考通过，二者都以拜师为前提，因此“拜师未拜师而正式守灯已确认”在实际游玩中不会出现。档案互斥的抽样不看门槛，仍枚举到这一组合：守塔期与码头期同时成立，彼此不是前置链上的祖先，检查器在 070 至 074 五个抽样年份各报一条档案冲突。

把林澜·守塔期的生效条件改为“正式守灯已确认，且港务署问责、学徒守灯以独自守灯、白棠在码头以指挥靠港、补考以再次未通过、出师考核以未通过都没有确认”。所引事件增至七个，状态组合共 15360 种，超过 4096，检查器提示后跳过林澜这个版本，结果为 0 错误、1 提示。

把补考“通过”分支的门槛改为“学徒对秦守的好感度属于 10”，检查器报两条错误：好感度不是有取值表的角色字段；它没有“10”这一取值。条件“角色状态”不能按数值设门槛。

### 模型

以开局方案“码头少年”开局，学徒没有拜师。叙事模型登记动态事件“学徒偷学灯语”，把学徒的灯语提升为名匠，把他对秦守的关系设定为师徒。这两条变化的路径、操作与取值都合法，协议写入，本局中学徒有了名匠的灯语与师徒关系；当前档案仍是少年期，因为学徒期的生效条件引用的是预设事件“拜师”以“拜师”确认。

### 上下文

以潮历072年开局，当前地点写为码头区的栈桥，消息为“码头上几个修船铺的学徒在搬木板。”。消息中的“学徒”是灯塔学徒的别名，路由把灯塔学徒列为被提及角色，尽管消息所说的是修船铺的学徒。

以潮历074年开局，当前地点写为灯塔的灯室。只有秦守在场时，在场角色一部分的 JSON 为 878 码点；启用周岚、为四个角色组完成初始化并都写为在场之后，为 3205 码点，其中周岚 688、灯塔学徒 869、白棠 747、秦守 827、玩家 68。协议文本 2597 字符、世界概况 174 字符，每轮相同。这些部分都不受预算约束。
