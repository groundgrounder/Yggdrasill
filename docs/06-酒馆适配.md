# 酒馆适配

酒馆适配把世界书、世界树内核与卡面合成为一张 SillyTavern（下称酒馆）角色卡，并在酒馆中维持每轮生成、记账、协议写入与回档。它不改变事件、命令或本局的事实来源。此前第一至第五章说明世界本身怎样组织和运行，本章说明这些规则怎样在酒馆里实际发生。

本章区分三种状态：已在原型中跑通并留有验收证据的行为、只验证了一部分的行为、仍等待实现的部分。后文的“当前实现状态”表以状态列标出每项属于哪一种。适配源码已迁至仓库顶层 `adapter/` 并纳入版本管理：`build.mjs` 负责打包与兼容指纹，`smoke.mjs` 在模拟宿主中做冒烟验证，运行时由 `runtime.mjs`、`settings.mjs`、`commands-parser.mjs`、`bookkeeper.mjs` 等模块分工。它仍是一次性原型，测试卡名与本机路径都不是正式接口；正式发布安装流程与旧存档自动迁移工具仍待交付。

## 模型与一轮时序

### 职责与信息隔离

适配层包含两类模型调用与一个确定性的命令转换步骤。它们按职责分开，不新增扮演世界或角色的模型角色。

| 部分 | 输入 | 输出 | 不得做的事 |
|---|---|---|---|
| 叙事模型 | 路由组装的本轮上下文、酒馆中的对话历史与玩家输入 | 本轮正文 | 默认记账时读写角色卡程序、生成记账 JSON 或直接改本局；读取楼层记录中的失败、命令与原始记账结果 |
| 记账调用 | 本局记账规则、正文之前的本局摘要、候选、待登记与将到事件、地点、可写字段、本轮玩家输入、待记账正文 | 一个记账 JSON 对象 | 写正文、续写聊天、选择与正文无关的状态、直接修改本局 |
| 命令转换 | 记账 JSON、世界书索引、协议可写字段与正文之前的本局 | 命令列表与转换错误 | 调用模型或绕过协议执行状态变化 |

叙事模型只负责叙述。默认记账时，它看到由路由选出的协议文本、世界概况、当前状态、在场人物、相关条目、经历、候选与待登记事件；协议文本在这一模式下要求它只写正文，不写命令。它看不到记账 JSON Schema、记账原文、每楼失败记录或调试面板。

记账调用只负责把已经写出的正文转换成结构化的变化。它使用独立的原始生成接口，即当前酒馆助手所暴露的 `generateRaw` 一类非聊天生成调用；请求以显式系统提示与用户提示组成，不追加成聊天楼，也不共享叙事轮的隐式提示状态。它看到正文之前的本局状态、当前玩家输入和正文，另看到解析正文所需的事件候选、待登记与将到事件、地点列表与可写字段。它不接收叙事轮的注入块，不读取酒馆对话中的其它楼层，也不生成可供玩家阅读的叙事。另设模型只更换这份记账请求所用的连接与模型，不增加第三个叙事参与者。

记账结果转成命令后，由适配层提交给协议。命令仍是确认事件、动态事件、确认初始化、写场景与待定项五种，命令语义、校验顺序、同轮逐条执行及失败边界仍按第四章执行。

### 推荐预设

叙事模型的主提示词与输出长度由酒馆预设提供。仓库在 `presets/yggdrasill.json` 给出一份可直接导入的预设：主提示词要求以叙述者身份只写正文，另有一条可编辑的输出长度提示。预设不定义记账调用、不写世界书、不代替卡内脚本，适配层也不读取它的内容；作者可以按自己的文风改写，协议与检查结果不受影响。

### 四种记账行为

记账由全局设置控制。没有保存设置时，默认行为如下。

| 行为 | 模型调用 | 正文约定 | 当前状态 |
|---|---|---|---|
| 默认记账，未保存设置 | 使用酒馆当前连接与模型，另发一次独立记账请求 | 叙事只写正文 | 记账开启，应答格式为提示词 JSON |
| 同一模型 | 使用酒馆当前连接与模型，另发一次独立记账请求 | 叙事只写正文 | 已实现 |
| 另设模型 | 记账使用单独配置的连接与模型，叙事仍用酒馆当前模型 | 叙事只写正文 | 已实现 |
| 关闭记账 | 不另发记账请求 | 叙事模型在正文末尾写 `<命令>` | 已实现，作为旧方式保留 |

“默认记账”是未保存设置时的完整行为，不是另一个模型角色。用户显式选择“同一模型”时，只复用当前连接与模型；正文完成后仍另发一次独立记账请求。这里增加的是记账调用，不增加模型角色。“另设模型”允许使用代理预设和酒馆连接设置，密钥只保存在酒馆的设置存储中，不进入楼层记录、角色卡或日志。

设置变化只影响其后产生的楼层。已经记账的楼层按其存下的命令重放，不因之后改用其它模型或关闭记账而重新解释正文。关闭记账后若楼层的有效记录带有命令，仍按记录重放；没有可用记录时才解析该楼正文中的旧命令。

### 一轮的完整时序

一次正常叙事轮按以下顺序执行：

1. 生成前先等待正在执行的记账与重算任务结束，检查当前聊天、当前 swipe 与最近可用前楼记录。记录缺失、归属失效或运行清单不兼容时，阻止生成并显示原因。
2. 按记账开关选定本轮协议文本与相应路由，以当前分支上最近可用的前楼本局为底调用路由。待登记事件按协议在有效本局上计算。
3. 将路由得到的本轮上下文以固定 id 注入一次。关闭记账时使用命令版协议文本；开启时使用只写正文的协议文本。本轮注入不得包含记账 JSON Schema。
4. 叙事模型生成本轮正文。正文是玩家看到并参与编辑的内容，不是命令记录。
5. 收到助手楼后，把该楼号、swipe、正文指纹和任务标识放入串行队列。任务在实际执行时重新核对这些值，已过时的任务不得写入。
6. 开启记账时，以正文之前的本局发出独立记账请求。每次重试都从同一底本开始，只追加上次的错误提示，不叠加已执行命令。关闭记账时，改为解析正文末尾的 `<命令>`。
7. 记账 JSON 先按固定字段和枚举校验，再确定性地转换为命令。命令经协议逐条执行，记录每条成功、未写入与失败的结果。
8. 把正文之前的本局、最终本局、可供重放的命令、失败、已写入、归属、记账信息和运行清单一次性写入该楼该 swipe 的记录。写入成功后才刷新当前本局、每楼记录与本轮上下文。

记账过程中不得再次触发同一轮的路由注入。记账调用若发出酒馆的生成前事件，适配层凭“记账进行中”标记立即返回，既不改注入，也不等待正在运行它的队列。调用期间临时移除本轮叙事注入，调用结束不重新注入上一轮的旧上下文；下一次叙事生成再按当时的本局重新路由。

队列以任务标识、聊天标识、楼号、swipe 与正文指纹共同校验。用户在记账完成前编辑、删除、切换 swipe 或切换聊天时，旧任务的结果作废，不得用旧正文的结果覆盖新正文的记录。叙事生成开始前必须等队列完成；记账请求本身不能递归等待队列。

### 触发模型与重放

“记账任务”表示一次逻辑记账，允许按设置重试，但不会并发启动。表中的“重放”只执行楼层已保存的命令，不调用模型。

| 触发 | 叙事模型 | 记账任务 | 本局与记录 |
|---|---|---|---|
| 打开尚未开局的新聊天 | 不调用 | 不调用 | 前端预演并最终封卷，应用开场命令后写第 0 楼记录 |
| 玩家发送消息 | 只登记消息 | 不调用 | 玩家楼不能作本局底本，可带从别处复制来的变量，但一律不信任 |
| 生成新的助手回复 | 调用一次 | 默认或启用时，正文完成后调用一次；关闭时不调用 | 从前楼底本执行本楼命令，写入本楼记录 |
| 选择已有 swipe | 不调用 | 不调用 | 重放所选 swipe 的命令，再按需要重放其后的楼层 |
| 新建空 swipe 或重新生成 | 调用一次 | 新正文完成后按设置调用或解析一次 | 旧 swipe 的记录保留，新 swipe 得到独立记录 |
| 继续生成 | 酒馆发起一次继续请求 | 对完整正文重新执行一次记账任务；关闭时解析完整正文 | 旧正文的命令记录先失效，按前楼底本重新计算本楼 |
| 编辑助手楼正文 | 不调用 | 启用时对整楼新正文记账一次；关闭时解析新正文 | 本楼重算，其后助手楼重放各自命令 |
| 编辑玩家楼正文 | 不调用 | 不调用 | 玩家楼的本局不参与计算，其后助手楼重放命令 |
| 删除楼层 | 不调用 | 不调用 | 从删除位置前最近可用本局起，重放保留楼层的命令 |
| 本楼重新记账 | 不调用 | 启用时调用一次；关闭时重新解析正文 | 本楼重算，其后楼层重放命令 |
| 重载聊天、切换聊天或切换到已保存 swipe | 不调用 | 不调用 | 校验归属与运行清单，恢复或重放记录；发现缺口即停止 |

重新生成时，路由排除将被替换的当前助手楼，避免把旧回复当成前文。存在多个 swipe 时，每次按当前选中的 swipe 计算，不得把其它分支的本局接在本分支之后。打开聊天时不自动补记账，以免加载动作产生不可预期的模型费用或覆盖历史。

### 记账请求与命令转换

记账请求有一个与传输方式无关的接口，至少返回系统提示、用户提示与 JSON Schema。Schema 对所有字段标为必填并禁止表外键。适配层可用两种方式发送：

- 结构化输出：把 Schema 作为请求的结构化输出参数发送。
- 提示词 JSON：把 Schema 与“只输出一个 JSON 对象”的要求写进系统提示。

两种方式得到相同的 JSON 形状和相同的协议校验。当前实测可用的是提示词 JSON；结构化输出是否受某端点支持不在本章假定。端点拒绝结构化输出时必须明确报错或按设置切换到提示词 JSON，不得把普通正文当 JSON 猜改。

记账结果的所有字段都必填，没有内容时使用空字符串或空列表：

| 字段 | 写法 |
|---|---|
| `时间` | `{方式, 日期, 事件ID}`，方式为 `不变`、`写日期`、`到事件开始`、`越过事件` |
| `地点` | `{地标, 场景}`，地标为空或地点库中的ID，场景为短语 |
| `在场` | 正文结束时除扮演角色组以外的在场角色组ID列表 |
| `发生的事件` | `{事件ID, 分支ID}` 列表，只取正文确实写出其发生的候选、待登记或将到事件 |
| `新情况` | `{事件ID, 摘要, 变化}` 列表，变化为 `{路径, 操作, 值}` 列表 |

校验使用记账模块实际生成的 Schema 子集：类型、必填字段、表外键、封闭枚举与列表形状。事件、分支与时间事件的引用不按封闭枚举拒绝，由转换层按世界书归属核对，因此“JSON 失败”与“转换错误”分开。这里不是完整的第三方 JSON Schema 实现。

命令转换遵守以下顺序：

1. 第一次出场且初始化方式为显式确认的角色组，先排入确认初始化；初始化按事件推进前的状态选择档案，再推进事件。
2. 正文中的发生事件按事件窗口的起点（`触发时间.最早`）排序，同刻按事件ID的码点顺序。事件窗口的起点晚于当前时间时，先把当前时间写到这个起点；起点不晚于当前时间时，不倒退时间，直接确认。结束事件与 `到事件开始` 的主键不变。
3. 处理时间的目标值。时间只能前进；目标早于正文之前的本局时报转换错误。事件ID或日期不合法时不生成对应写场景。
4. 目标时间、当前地点与在场分别生成独立的写场景，顺序为：确认初始化、事件起点时间与确认事件、目标时间、地点、在场。任一条被协议拒绝只影响该条，其余合法变化照常提交。换场先于离场写入；原在场而本轮离场的角色，其 `所在` 显式写为换场前的地标，不能因为拆成两条命令而丢成新地点。
5. 地点写场景的 `场景` 以模型给出的短语为准。模型留空时，只有地标未变才沿用旧场景；地标改变或旧场景也为空时，`场景` 写作新地标，不能把旧地标的场景带到新地标。
6. 按正文之前的在场状态计算差异，只在有变化时生成写场景。
7. 按记账结果的原顺序生成本轮动态事件，并逐条校验ID、摘要、操作和值。
8. 无法解析、引用世界书外对象或写到不可写字段的条目形成转换错误；其余合法的命令仍提交。

命令转换不得依赖模型自然语言里的“大概发生了什么”。记账输出只提供与正文对应的事件、分支、时间与变化，路径和枚举由 Schema、世界书索引和协议共同约束。

### 失败与状态边界

楼层记录必须成功写入，并通过归属、记录格式和运行清单校验，才能作为后续底本。楼内记账失败、转换失败或部分命令失败时，记录中保存的本局只能是正文前底本或协议实际确认的部分提交，按失败表处理。不要求楼内所有命令成功才能使用记录，也不得把失败项当作已执行。

| 阶段 | 反馈 | 状态边界与重试 |
|---|---|---|
| 路由、封卷或记录校验失败 | 阻止本轮生成，显示失败原因 | 不写新记录；修复选择、记录或兼容性后重试 |
| 叙事调用失败 | 由酒馆显示调用错误，正文楼没有成功记录 | 不运行记账，不伪造空正文或状态变化 |
| 记账调用失败 | 该楼显示“记账调用失败”，调试时附错误 | 本局保存为正文之前的底本，命令为 `null`，重试从底本开始 |
| JSON 解析、字段缺失或枚举不合法 | 该楼显示“JSON 失败”及尝试次数 | 本局保存为底本，命令为 `null`；下一次尝试附上上次问题 |
| 记账转换拒绝单个项目 | 显示转换错误数，调试时列明项目和错误码 | 其余合法命令照常执行；被拒绝项不进入可重放命令 |
| 协议拒绝部分命令 | 显示失败数与楼号，调试时列序号、命令名、错误码与说明 | 已完成命令留在本局和重放列表；失败命令不重放，其后命令按协议继续 |
| 执行器异常，无法确定提交边界 | 该楼显示执行失败 | 保留正文之前的底本，不保存不可确认的部分结果 |
| 全部成功 | 每楼记录显示变化摘要，或按设置只显示一行 | 保存最终本局与实际执行过的命令 |

记账失败不交给叙事模型续写。关闭记账时，旧的正文命令失败可以按下一条正文命令的反馈规则提示叙事模型重写；启用记账时，失败只在玩家界面显示，玩家可先点本楼“重新记账”。允许继续生成时，后续路由只使用已提交的本局，不把失败识别成成功。

## 前端与打包

### 角色卡的三部分

正式角色卡由三部分组成：

| 部分 | 内容 | 来源 |
|---|---|---|
| 世界书 | `世界书/` 下的全部运行文件与 `yggdrasill.yaml` 的运行参数 | 作者的世界书项目 |
| 程序 | 内核、适配层、内存文件系统、路由注入、记账、命令转换、楼层记录、界面脚本与协议文本模板 | 与卡一起构建并内嵌，不依赖独立扩展或远程运行时 |
| 卡面 | 名称、描述、头像、开场白、默认开局选择与开场命令 | 作者的卡面源文件 |

打包输入是已通过检查的卡项目、卡面源文件、世界树源码与固定版本的模板。打包输出是可直接导入的角色卡 JSON 或 PNG，以及构建清单。世界书正文不另存为运行时可替换的外部文件；角色卡载入后由内存文件系统提供与构建清单一致的文件树。

正式打包依次执行：

1. 读取并规范化卡面，拒绝缺少必填字段的卡面。
2. 对世界书运行静态检查；存在错误时停止。
3. 收集并规范化世界书文件，计算世界书哈希。
4. 收集适配层、内核与模板，确定程序版本并计算程序指纹。
5. 生成构建清单，把世界书文件、卡面默认值与清单嵌入程序或酒馆助手数据；模板随程序一起打包。
6. 把程序打成单个脚本，生成固定的脚本标识与局部正则标识。
7. 写出角色卡与构建清单，验证卡内脚本、世界书哈希、卡ID与清单一致后才算成功。

作者资料不属于运行世界书，默认不进入角色卡。若某类作者资料以后需要随卡分发，须另立字段与检查，不能因为原型曾临时打包出处文件就视为正式规则。

### 卡面与开场

卡面源文件的最小字段是 `卡ID`、`卡版本`、`名称`、`描述` 与 `开场白`。字段层面 `开局` 与 `开场命令` 可以省略；正常可玩卡的构建必须提供默认 `开局` 映射，缺少时构建失败。`开场命令` 可以省略。

| 字段 | 作用 | 约束 |
|---|---|---|
| `卡ID` | 识别同一张卡的连续版本 | 跨版本稳定，不得随显示名改变 |
| `卡版本` | 供作者识别人工版本 | 不代替哈希，不单独决定兼容 |
| `名称`、`描述` | 卡面展示与叙事角色说明 | 不写命令语法、随运行模式变化或与当前分工冲突的长期指令；可保留“本局状态由系统维护”这类稳定的职责说明 |
| `开场白` | 玩家看到的第一段正文 | 纯正文，不把命令、JSON Schema 或调试说明当作可见聊天内容 |
| `开局` | 开局的默认时间、方案、角色组、玩家与历史选择 | 是开局的初值，不是封卷后的可变状态 |
| `开场命令` | 开场白出现后、第一次路由前的命令列表 | 由适配层执行，不能由模型解释成正文 |

开场白与开局参数分离。开场白描述玩家进入的场面，不负责封卷，也不靠正文里的隐藏命令决定开局时间或角色版本。默认 `开局` 被开局前端作为初值；最终选择经协议封卷后写入开局设定，此后以本局中的开局设定为准。`开场命令` 只在新建聊天时执行，用于初始化第 0 楼需要的场景和角色；重载时直接重放第 0 楼记录。

开场白不承载开局参数或命令。原型在构建时拒绝包含 `<命令>` 的开场白，开局前端以卡面 `开局` 为初值。卡面字段的要求见上表。

开场命令按最终封卷的玩家调整后再执行。当前地点写入之后，扮演角色组自动视为在场并跟随当前地点，协议不允许用写场景改写它；因此适配层在封卷成功后，从每条 `写场景` 的 `在场` 与 `所在` 中删去扮演角色组，删空的映射整键省略，写场景因此变空则整条省略。其余命令、其他角色、时间与地点保持不变，开场命令中已有的 `确认初始化` 不改；自建模式或命令未命中扮演角色组时逐字执行。第 0 楼记录保存实际执行的命令，重载时按这份命令重放。畸形命令不在此修补，仍由协议校验拒绝。

### 打包路径与内存文件系统

打包把世界书映射为“规范化路径 → UTF-8 文本”。路径以 `/` 分隔，运行世界书根固定为 `/项目/世界书`，运行参数位于 `/项目/yggdrasill.yaml`。路径不得是操作系统绝对路径，不得含 `..`、空段或重复规范化后的同名文件；符号链接不跟随。打包清单按路径的码点顺序记录每份文件的哈希和长度。

世界书哈希按以下可复算方式得到：先对每份文件求内容 SHA-256，再把 `[规范化路径, 内容SHA-256]` 按路径码点顺序排成数组，以无多余空白的 JSON 序列化后对 UTF-8 字节求 SHA-256。算法须固定写入构建工具，不能因操作系统、目录遍历顺序或换行转换而变化。

运行时通过统一内存文件系统提供 `readFile`、`readdir`、`join`、`dirname`、`extname` 与 `resolve`。声明读取、世界书载入、运行参数读取、检查器与路由都必须挂载同一个内存根，不能一部分读卡内文件、另一部分读宿主磁盘。缺失目录、缺失文件或路径逃逸须中止载入并显示错误。

脚本、内核、模板和世界书来自同一次构建。构建工具可重复接受 `--compatible <旧程序指纹>`，把明确核对过的旧程序写进清单的 `兼容程序`；不读取或回填任何固定旧值。运行时不得联网替换核心、加载另一张卡的世界书或接收宿主任意路径。内核随卡内程序一起锁定，不能单独从外部升级；内核、适配层或模板的任何变化都要反映到新的程序指纹。卡内清单同时记录 `卡ID`、`卡版本`、`程序版本`、`记录格式`、`程序指纹`、`世界书哈希` 与 `兼容程序`。程序指纹的排布与哈希算法同世界书哈希，输入为内核、适配层与模板的规范化路径和内容哈希；世界书哈希对运行世界书计算。二者缺一不能把一次构建视为可识别。

### 权限与安全边界

卡内脚本与局部正则都必须在酒馆导入或启用时取得用户允许。适配层在脚本确实运行时检查宿主的 API 完整性、当前卡内脚本标识与启用字段；关闭记账时另检查局部正则的标识、`placement`、`disabled` 与 `character_allowed_regex`。任一项不满足时，界面显示独立的“权限不足”说明，生成前清除本轮注入并阻止生成；不得误写成存档只读，也不得通过改文件名、嵌入第二份脚本、绕过酒馆 API 或假设用户已允许来规避。

脚本根本没有执行时，卡内代码无从自检，只能依赖导入说明与宿主自己的拒绝提示；文档与卡面不声称脚本能发现“自己未运行”。局部正则只用于隐藏关闭记账时正文中的旧命令块。它的匹配范围、替换文字与启用状态要固定；它不得改写聊天原文、注入命令或访问网络。默认记账的正文不含命令，不依赖该正则，因此局部正则问题只在关闭记账时阻断生成。

模型输出一律按不可信输入处理。记账文本只经 JSON 解析、Schema 校验、世界书索引与协议校验；命令不能使用 `eval`，不能写入未声明的对象键，不能借用 `__proto__`、`constructor` 或 `prototype` 扩展宿主对象。生成请求只走酒馆助手提供的模型接口和用户明确配置的连接，不另开远程运行时。密钥、原始提示与模型结果不得进入卡面、普通楼层记录或报告；调试原值只能留在当前聊天的可选调试数据中。

### 界面范围

适配层提供以下界面能力，不规定视觉稿：

- 本局面板：普通模式只显示玩家已经知道的时间、地点、在场者、认识的人、经历与进行中的事件串。候选、将到、已排除和调试信息只在调试模式出现。
- 每楼记录：显示该助手楼的变化摘要、失败计数与失败原因，展开后显示可读的已写入项；助手楼可对该楼重新记账。
- 调试面板：显示较完整的事件状态、记账调用看到的事件、楼层命令、原始记账结果、转换错误与协议失败。
- 本轮上下文：显示最近一次叙事生成前实际注入的文本与路由审计；这些内容在离开聊天或重新路由后不再保证存在，也不持久化为本局字段。
- 设置：记账方式、应答格式、同模型或另设模型所需参数、温度、最大长度、尝试次数、每楼记录与调试开关。
- 重新记账：每楼按钮只以该楼新的正文重算本楼，再重放其后楼层；总按钮作用于最近一楼的助手楼。关闭记账时改为重新解析正文命令。

派生视图不写回本局。每楼记录、本局面板、调试结果与设置说明都不进入叙事或记账提示。玩家面板不得因为调试开关之外的原因展示尚未发生的事件 ID、候选分支或原始记账 JSON。

### 开局前端

开局前端已在原型中实现并验证。正式产品化的界面与发布流程仍未交付。它接收以下五类选择，并最终原样组成封卷输入：

| 选择 | 规则 |
|---|---|
| 开局时间 | 没有方案提供时间时必填；按卡声明的纪年校验 |
| 开局方案 | 作者预设的组合，可提供开局时间、角色组与历史选择；直接选择覆盖方案中的同项 |
| 角色组 | 按角色组合并启用状态与版本；只在已声明的版本中选择，扮演角色组必须启用 |
| 玩家 | 自建玩家或扮演角色组；自建档案按协议可接受的形状提交 |
| 历史选择 | 只能选择已声明的开局选项；每项取可用分支ID或“未发生”；自由组合关闭时只从方案默认值派生 |

每次选择变化时，前端在内存副本上合并当前选择并调用协议封卷预演，不调用叙事或记账。预演成功才更新界面显示的可选分支、可用角色组和预览；失败时保留上一次有效的预览，显示协议错误，不能把失败草稿写入聊天变量或显示成已开局。

提交开局时重新执行一次完整封卷，不以预览结果为事实。随后在内存中依次执行 `开场命令`，任何一条失败即丢弃本次草稿，不创建第 0 楼记录，也不产生半份本局。全部成功后，把第 0 楼的正文归属、本局、命令、已写入、空失败与运行清单一次写入，再展示开场白并启动第一次路由。重复提交须先核对聊天尚无可用的开局记录。

## 变量、回档与升级

### 唯一事实源

每局只有一个剧情状态事实源，即该局的本局对象。楼层的 `本局` 是按已提交命令得到的快照，历史快照与当前快照属于同一个状态，不是第二份世界状态。当前档案、当前能力、可用技能、事件有效状态、事件串状态、玩家面板与提示词都不写回楼层变量。

同一楼不同 swipe 各有一份记录。记录失效时，正文仍由酒馆保存，适配层不得改写正文来修复状态。

### 楼层记录

每个需要本局的助手楼和有效第 0 楼都写一份记录。记录存放在该楼、该 swipe 消息变量的固定键 `世界树` 下；玩家楼即使收到复制变量也不形成可用记录。

| 键 | 必需 | 内容 |
|---|---|---|
| `记录格式` | 是 | 整数版本；当前正式格式为第一版 |
| `运行清单` | 是 | 仅七项兼容判定字段：`卡ID`、`卡版本`、`程序版本`、`记录格式`、`程序指纹`、`世界书哈希`、`兼容程序`；文件明细留在构建清单里 |
| `归属` | 是 | 楼号与正文指纹；正文变化后指纹失配 |
| `本局` | 是 | 执行本楼成功命令后的完整本局；失败时为本楼之前的底本或最后一个可确认提交 |
| `命令` | 是 | 可重放的命令列表，或 `null` 表示没有可复用命令 |
| `失败` | 是 | 失败列表；每项至少有阶段、错误码与说明，有命令序号时附命令序号与命令名 |
| `已写入` | 是 | 协议返回的已写入摘要，顺序与执行一致 |
| `记账` | 是 | `方式`、`应答格式`、`状态`、`尝试次数`；可选模型名、原始结果与错误摘要 |

每楼只保存上述七字段副本，不再复制世界书与程序的逐文件明细；旧聊天中带完整构建清单的记录仍按同一 `manifestIssue` 校验读取，不需要迁移。第 0 楼与关闭记账的旧方式也在 `记账` 中明确写 `开场命令` 或 `正文`，不能以缺少字段表示不使用模型。`命令` 为空列表表示记账成功但没有产生命令；`null` 表示调用、解析或提交边界失败，没有可重放命令。两者不能混用。原始记账结果只在调试开启时保留，且不得包含连接密钥。`本局` 与可重放命令必须同时满足运行清单；仅凭一个形状相同的对象不能认定兼容。

正文指纹是正文 UTF-8 字节的 SHA-256。记录同时保存楼号；归属只在楼号、角色、当前 swipe 与正文指纹全部相符时成立。旧版没有归属字段的记录不能自动补成当前格式。

### 底本、重放与失配

计算第 n 楼时，从 n 之前向下找最近一份可作底本的记录。只接受助手楼或有效第 0 楼，且其归属、记录格式、运行清单与当前卡一致。玩家楼、归属失配的记录、运行清单不一致的记录都不能作底本。

如果中间某个助手楼缺少记录或记录失效，不能跳过它继续使用更早的快照，因为这会把该楼可能发生的变化静默丢掉。当前楼是新生成、正在重新记账或新 swipe 时，允许该楼自身暂时没有记录；它之前的所有助手楼仍须完整。

正常载入与切换时，从第 0 楼开始依次核对记录。每楼用前一本局重放其命令，重放结果必须与记录的 `本局` 一致；不一致的记录视为失效。发现缺口时保留已有变量，停止自动计算和生成，显示“需要重新记账”或“存档不兼容”。

重算规则如下：

- 选择已有 swipe：从该楼之前最近的可信本局开始，重放该 swipe 的记录，再重放其后助手楼的命令。全过程不调用模型。
- 新建空 swipe 或重新生成：空 swipe 不参与本局；生成完成后按本楼新正文取得命令。旧 swipe 的正文与记录均保留。
- 继续生成：本楼正文已经改变，原记录失效。以之前本局为底，对完整新正文重新取得命令，避免只对追加部分记账而重复前半段变化。
- 编辑助手楼：以之前本局为底重新取得本楼命令，再重放其后助手楼的命令。
- 编辑玩家楼：不改变已经提交的助手命令，直接重放其后楼层；玩家楼携带的任何本局记录都忽略。
- 删除楼层：从删除位置之前最近的可信本局开始，重放保留下来的助手楼命令。删除造成记录缺口时停止，不用旧快照冒充结果。
- 重载与切换聊天：只校验和重放，不自动向模型补记账。当前选中的 swipe 决定当前分支。

每个楼层的记录在内存中计算完整，再通过一次变量替换提交。提交失败时保留旧变量并在界面提示未保存。重算期间整楼显示“记账中”，不得让路由读到尚未提交的草稿。

编辑、切换 swipe 或删除前楼后，被重放的下游命令可能因新的本局而不再合法。此时按协议保留已经成功的命令，写入部分状态与失败，继续按协议处理同楼其余命令，但不自动调用模型重写该楼；在玩家查看或重新记账之前，停止从该楼继续生成。正常重载时若重放结果与保存快照不同，不把差异当成可自动修复，直接将该楼标为失效。

### 设置存储

适配设置存放在酒馆全局变量的固定键 `世界树·记账` 下，不属于某一局，也不随卡面导出。设置对象包含记账方式、应答格式、同一模型或另设模型参数、温度、最大长度、尝试次数、每楼记录与调试开关。

设置写入使用一个串行队列。每次修改先与队列中最新值合并，再写入酒馆存储；连续快速修改不得互相覆盖。关闭设置界面时先等待队列结束，再从酒馆设置存储读回刚写入的键值；读回一致才允许关闭。超时、读取失败或值不一致时保持界面打开并显示错误，不能把内存中的值当成已保存。

设置不进入本局统一事实源，也不改变历史楼层。切换聊天后设置继续生效；切换记账方式不会追溯重算旧楼层。

### 卡、世界书与旧记录

卡面版本只供人识别，正式兼容由运行清单判断。载入聊天时，逐楼读取 `卡ID`、`记录格式`、`程序指纹`、`世界书哈希` 与当前构建清单比对。

| 情况 | 处理 |
|---|---|
| 卡ID、记录格式、程序指纹与世界书哈希都一致 | 正常载入，校验归属并重放命令 |
| 程序指纹不同，但旧指纹在当前 `兼容程序` 列表中，卡ID和格式一致，世界书哈希也一致 | 可按兼容程序载入；界面提示已使用的程序版本 |
| 世界书哈希不同 | 当前卡不自动迁移，停止写入与生成，保留原聊天供导出 |
| 记录格式不同，或卡ID不同 | 不自动迁移，停止写入与生成 |
| 同一聊天混有不同卡ID、记录格式或互不兼容的程序 | 整局视为不一致，停止写入与生成 |
| 没有运行清单、没有归属或属于旧版未验证记录 | 视为旧记录，不猜测其字段含义，不自动补写 |

程序升级只有在构建清单明确列入兼容旧程序指纹时才算可确认兼容。只提高卡版本号、只保持相同文件路径或仅凭 JSON 形状相同，都不足以证明兼容。世界书内容变化一律不静默继承旧局；若以后需要迁移，须另行设计可检查的逐事件与逐字段迁移工具，并单独验收。

遇到世界书哈希不同、记录格式不同、旧记录或混合版本时，适配层必须保留原始楼层变量并拒绝对聊天做以下操作：自动重算并覆盖、自动记账、提交新命令、静默删除失败字段。可以做的只有只读展示、导出原始记录和无损备份。继续游玩应新建聊天并使用兼容的卡；在迁移工具通过验收前，不承诺旧存档自动升级。
