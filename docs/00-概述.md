# 概述

世界树是为 SillyTavern（下称酒馆）的角色卡制定的规范及其工具链，面向依据长篇原作改编、人物与事件众多、时间跨度大的角色卡，也适用于作者原创的世界。它的价值首先在于：尽可能多地保留原作的内容，同时使每轮的提示词保持精简；其次在于：作者可以自由地设计 if 线。本文先说明这类卡面对的困难，再依次说明世界树怎样保留原作、怎样精简上下文、怎样承载 if 线、怎样便于维护，最后说明项目的现状。各项机制的细节见第一至第六章。

## 问题

改编长篇原作的角色卡，面对保留与精简的两难。原作中的人物、事件、台词与设定，保留得越多，模型越能贴近原作。可是这些内容写进提示词，提示词随之变长，模型越难抓住此刻真正相关的部分。按关键词触发的世界书条目，以最近的消息中是否出现某个词决定是否插入，插入与否取决于用词，而不取决于剧情走到了哪里：后来才发生的事，只要它的关键词出现，也会被插入；角色在不同时期的设定写在同一处描述里，模型分不清此刻适用哪一部分。

即使改用 EJS 模板按日期查表载入剧情、按年份切分人物设定，或采用 MVU 等正文末尾内联变量更新方案，依然存在三类难题：其一，剧情与角色只认日期或年龄、不认因果，一旦玩家改写关键事件，下游剧情不会自动截断，角色也会按岁数硬切到原作身份；其二，叙事模型写完正文还要在同一次回复末尾兼写变量补丁，每轮需常驻较长的更新规则，既挤占上下文，写错格式也会污染正文；其三，条目与脚本分散在界面手工维护，逻辑冲突要到游玩时才会暴露。

改编的另一层吸引力是 if 线：开局时某件事没有发生，或者游玩中走了另一条路，后面的人物与事件随之改变。按原作的先后写成的设定，默认后面的事都会照原作发生，任何一处偏离都会使下游的内容失去依据，而作者很难查明某处偏离波及哪些内容。

## 原作

世界树把原作的内容写在世界书中，而不是写进提示词。原作的走向写成事件：每个事件写明它可以发生的时段、前提、缺之不可的角色与可能的分支，原作中实际发生的走向通常就是默认分支。事件可以按原作逐章抽取。角色在事件中的视角、所知与所记，写在角色位置中。原作中角色说过的话，即原台词，逐字收入角色位置的候选台词，排在作者撰写的台词之前，出处记在作者资料中，正文不标注。角色按时期写成档案，每份档案只写这一时期及以前已经确立的事实。技能、装备、地点、势力等公共的设定，写成条目库中的条目（见第二、三章，以及第一章“条目库”）。

这些内容保留在世界书中的数量，不受每轮提示词的限制。作者可以把原作的事件、各个时期的人物与原台词尽量完整地写下来。玩家得到的，是按原作的时间展开、人物在各个时期言行有据的世界。

## 上下文

世界书中的内容不是每轮全部交给模型。路由每轮按本局的状态挑选：在场的角色只给当前适用的那份档案；已经发生的事件，只选入与当前地点、在场者或最近的消息相关的若干件；此刻可以发生的事件，只给出它可以走向的分支，当事人的记忆要等事件确认之后才给出；条目只选入在场者持有或能用的、当前地点所在的与消息中提到的。经历、候选与各条目库各有条数或字符的预算，放不下的整条略过（见第五章）。

挑选依据的是剧情的进度，而不是用词。尚未发生的事件不会作为经历出现，档案不提及之后才出现的人与事，原作中后来的内容因此不会提前进入上下文。世界书写得再多，按上述方式挑选的部分，规模由预算与当前的场景决定，不随世界书的规模增长。另有一些部分每轮都输出：协议文本，其中有全部的地点与可写的字段；世界概况；在场角色的完整档案。它们随卡的规模与在场的人数增长，不受预算约束（见第五章）。

## if线

世界树中的全部事件由门槛连成事件树，原作的走向、作者的改编与 if 线，在结构上没有区别，都是事件树中的路径。门槛只写真正的因果，即“没有它，这件事就不会发生”，而不写“原作中它排在前面”。世界层面的事件与它对各人的后果分开写，后果按当时各人身在何处、与谁同处、彼此是什么关系分流。偏离某处时，只有确实依赖它的事件随之改变，其余的照常发生（见第三章）。

if 线有两个入口。开局时，玩家可以在作者声明的开局选项中选择开局之前的历史，例如某个角色是否拜了师，作者也可以把若干选择组合起来，预设为开局方案。游玩中，叙事正文在门槛成立的分支中写出走向，也可以写出世界书中没有预写的动态事件，由记账结果或关闭记账时的正文命令登记。if 线的结构由检查器核对：前置事件是否在时间上先于后续事件，事件与分支在宽松的假设下是否可能发生，自动发生的事件在所有分支都走不通时是否仍有着落，开局方案与开局选项能否开局（见第三、四章）。

## 维护

世界书中的字段分为五层：架构、背景设定、内容、通用文本规范与本卡文本规范，每层由谁规定、改动之后检查什么，各有规定。卡的种类与取值只在 `设定/` 中声明一次，给模型的规则清单在打包时由声明生成，检查器与协议都读取声明，不写死任何卡的取值。改动背景设定之后，全量检查列出所有因此不再合法的内容，不再合法之处须显式迁移，不会被静默丢弃。游玩中的状态集中存放在本局中，只经事件与命令写入；写入本局的所有命令都由程序校验之后执行（见第一、四、六章）。

对作者而言，内容越多，越需要这些保证。改动的影响可以查出，清单不必在几处同步，结构的错误在写卡时就被指出。对玩家而言，角色学会的技能、结下的关系、身处的地点记在本局，前后一致，不依赖模型的记忆。

## 现状

世界树目前包含规范正本、内核、检查器、命令行工具 `ygg`（`check`、`trace`、`if`、`preview`、`context`、`tree`、`status`、`init`、`view`、`format`）、公开示例世界书《三国演义》（`examples/三国演义/`），以及位于 `adapter/` 的酒馆适配实现。内核实现协议与路由，检查器与协议共用同一套校验并由一致性测试覆盖；内部自动化测试夹具位于 `test/fixtures/雾港/`。

酒馆适配层已在真实酒馆与模拟宿主中跑通核心流程，包括叙事与独立记账分工、自动防倒退修补与每楼手动修补、开局五类选择与原子封卷、卡内离线打包、楼层重放、空尾楼防误锁与删楼自愈，以及世界书更新时的 A/B/C 三级兼容升级。已验证范围与待交付项详见[第六章“酒馆适配”](06-酒馆适配.md#实现状态)。

作者工具已交付十个命令行子命令 `check`、`trace`、`if`、`preview`、`context`、`tree`、`status`、`init`、`view`、`format`、九个分层作者 skill（详见[`skills/README.md`](../skills/README.md)）与本地作者视图 `ygg view`（详见[作者视图](../view/README.md)）。其中 `ygg tree` 的原台词与来源原文逐字一致由作者人工核对，不在工具自动核对范围；超长篇原作完整迁移后的提示词规模，待迁移案例完成后另作实测。
